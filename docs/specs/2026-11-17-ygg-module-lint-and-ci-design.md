# RFC-062: Проверка модулей до установки — `ygg lint` и reusable workflow `module-check`

* **Дата:** 2026-11-17
* **Статус:** черновик, на утверждении
* **Issues:** #23, #38 (связаны: #21, #35; следующие этапы: #39, #37)
* **Затрагивает:** новый `src/lint.nu`, `bin/ygg.nu` (`main lint`, completions), `src/pkg.nu` (таблица проб пакетов), `src/manifest.nu` (перечисление всех scopes без активации), новый `.github/workflows/module-check.yml`, `scripts/release.nu` (версия по умолчанию в workflow), `.github/workflows/ci.yml`, `tests/`, `README.md`, `.agents/skills/ygg-module-verification/`

---

## 1. Зачем

Тесты движка зелёные, а модули ломаются только при установке на реальный хост. При переносе пользовательских модулей на Linux и Windows так всплыли:

* отсутствующие источники ссылок, в том числе в неактивном `[scope.work.links]`: `ygg add` без этого scope их вообще не проверяет (#23), а сообщение указывает на уже удалённый staged-клон (#21);
* ошибки, которые видны только на целевой ОС: неверные ID пакетов `winget`/`scoop`, конфликты целей ссылок, которые проявляются лишь при определённом наборе scopes.

У репозиториев модулей нет CI. Единственная проверка модулей в движке — `tests/test_phase2_modules.nu` — привязана к путям и именам модулей одной машины и Unix-утилитам (#35), поэтому не переносима ни в CI модулей, ни на другую машину.

Нужна одна проверка, которая запускается одинаково локально, в pre-push hook и в CI модуля, и ловит этот класс ошибок до `git push` или до merge.

## 2. Цели, не-цели, анти-цели

**Цели**
1. `ygg lint [path]` проверяет модуль, не трогая хост: TOML-схемы, источники во **всех** `[scope.*]`, синтаксис выражений scopes и `setup.nu`, план `apply` для каждой ОС модуля и набора scopes, существование пакетов (по флагу).
2. Одна и та же команда — локально, в pre-push hook и в CI.
3. Модуль подключает CI пятью строками: `uses: gidragir/ygg/.github/workflows/module-check.yml@vX.Y.Z`. Вся логика проверок — в `ygg lint`, в YAML только установка окружения и вызов.
4. CI запускается на каждый push и PR модуля и проверяет его на всех ОС из поля `os`.
5. Работает на Linux, Windows 11/Server (Non-Admin) и macOS на чистом Nushell.

**Не-цели**
* Реальная установка пакетов и релизы модулей — #39 (workflow на тег).
* Откат модулей на версию — #37.
* Состояние конкретного хоста: файлы, занятые процессами (#22), реальные каталоги на месте целей, содержимое `secrets.toml` пользователя. Это остаётся за `preflight-check` при `apply` и за `doctor`.
* Запуск `setup.nu` и проверка значений секретов.
* Проверка существования версий (`node@22`), только имени пакета.

**Анти-цели** (провал, даже если «работает»)
* Второй валидатор: проверки, написанные в YAML, bash или отдельном Action, расходятся с ядром — ровно это и дало «тесты зелёные, а на хосте ломается».
* `lint` что-то меняет: реальные `~/.ygg`, `$HOME`, `host.toml`, `.state/`, создаёт каталоги вне собственного временного.
* Нестабильный по умолчанию локальный запуск: сетевые пробы пакетов только по `--packages`; сбой сети — предупреждение, не ошибка.
* Знание о личных модулях в движке (имена, пути, ожидаемые файлы) — инвариант §2.2, #35.

## 3. Ограничения

* `lint` — read-only команда того же класса, что `doctor`/`diff`/`status` (AGENTS.md §2.1): без `ensure-ygg-dirs`, `mkdir`/`save` вне собственного временного каталога, без `progress-step`, `--label`, `--progress` и `ygg-proc-*.log`, без host-lock.
* Временные `YGG_HOME` и `HOME`-песочница создаются через `mktemp` и удаляются в `finally`-ветке, в том числе при ошибке.
* Nushell `0.116.1` (как в `ci.yml`), без внешних утилит в ядре, кроме самих пакетных менеджеров для проб и `docker`/`podman` для compose.
* Раннеры GitHub одноразовые, но `lint` в CI работает так же, как локально: в песочнице. Раннеры Windows — с правами администратора, поэтому поведение Non-Admin CI не доказывает.
* RFC-061 (в работе) меняет формат сообщений `preflight-check` (#21). `lint` использует тот же форматтер и не заводит свой.

## 4. Подходы

| Подход | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. Логика в ядре (`ygg lint`), тонкий reusable workflow** | Один валидатор для хоста, pre-push и CI; версия проверок = версия движка | Нужна новая команда ядра | **Выбран** |
| B. Отдельный Action со своими проверками | Быстро начать | Второй валидатор (анти-цель), bash ломает кроссплатформенность | Отклонён |
| C. Полный workflow копируется в каждый модуль | Модуль независим | Правки разносятся руками по всем репозиториям | Отклонён; копируется только вызов из пяти строк |

Решения пользователя: подход A; на каждый push — статические проверки, план и проверка существования пакетов («уровень B»); реальная установка — только на релизный тег («уровень C», #39).

## 5. Дизайн

### 5.1. Команда `ygg lint`

```text
ygg lint [path] [--packages] [--os <list>] [--json]
```

* `path` — каталог модуля, по умолчанию текущий.
* `--packages` — включить пробы существования пакетов (§5.3, L6).
* `--os` — ограничить ОС плана подмножеством поля `os` модуля (по умолчанию — все ОС модуля).
* `--json` — находки в формате `doctor --json` (`finding` в [src/doctor.nu](../../src/doctor.nu#L20-L22)): список записей `{check, severity, target, detail, fix}`. Для L1–L4 `target` — путь относительно корня модуля с файлом и секцией объявления (`links.toml [scope.work] opencode`); для L5 — `<модуль>: <ключ>`, как в проблемах `preflight-check`. У находок L5 есть дополнительные поля `os`, `scopes` и `cross_os` (§5.3).
* Код выхода: `1`, если есть хотя бы одна находка `error`; `warn` и `info` код не меняют.
* Человекочитаемый вывод — в stdout (как у `doctor`); статусного вывода в stderr нет.

### 5.2. Изоляция

`lint` выполняет все стадии с собственными переменными окружения:

* `YGG_HOME` — временный каталог; реальный `YGG_HOME` и `~/.ygg` не читаются;
* `YGG_SANDBOX` — временная домашняя папка;
* `YGG_MOCK_PKG_LOG` — файл во временном каталоге (план не запускает менеджеры);
* для плана чужой ОС — `YGG_HOST_OS_OVERRIDE=<os>` (§5.3, L5).

Модуль подаётся в план как виртуальная запись (`--extra-modules`, RFC-012), без копирования в `modules/` и без `host.toml`.

### 5.3. Стадии

| Стадия | Что проверяет | Severity при нарушении |
|---|---|---|
| **L1 схемы** | `ygg.toml` через `load-module-manifest`; парсинг `packages.toml`, `links.toml`, `env.toml`, `aliases.toml`, `services.toml`, `secrets.example.toml`; неизвестные ключи верхнего уровня **только в `ygg.toml`** (например, `[scopes.x]` вместо `[scope.x]`; в `links.toml`/`env.toml`/`aliases.toml` любой нерезервированный ключ — это запись, и опечатка проявится как ошибка формы записи или отсутствующего источника); неизвестные менеджеры в `[packages]` и `[scope.*.packages]`; значения `os` из известного набора | `error`; неизвестный ключ верхнего уровня `ygg.toml` — `warn` |
| **L2 источники** | Собственный обход исходных файлов (`ygg.toml`, `links.toml`) — не через объединённый манифест, который теряет файл-источник записи. Каждый источник ссылок (включая скрипты `bin/`, это тоже ссылки), `[save]` и файлы `[containers]` — в базовых секциях и во **всех** `[scope.*]` — существует в модуле; `mode = "dir"` указывает на каталог. `preflight-check` здесь не подходит: он проверяет источники только ссылок и только активных scopes | `error` |
| **L3 scopes** | Каждый ключ `[scope.*]` разбирается `eval-scope-expression` без ошибок | `error` |
| **L4 setup.nu** | `nu -I <src движка> -c "nu-check setup.nu"` — с тем же include-путём, с которым ядро запускает `setup.nu` ([src/sdk.nu:361](../../src/sdk.nu#L361)); при неудаче текст диагностики берётся из `nu --ide-check` (сам `--ide-check` возвращает 0 и при ошибках, поэтому решение принимает `nu-check`) | `error` |
| **L5 план** | Для каждой ОС × набора scopes: `resolve-effective-plan` → `resolve-link-targets` → `compute-link-ops` → `preflight-check` в песочнице. Ловит конфликты вложенности и затенения, коллизии целей между секциями, ошибки разрешения путей | `error` |
| **L6 пакеты** (`--packages`) | Каждый пакет каждого менеджера, доступного для пробы на этом хосте, существует (§5.4) | не найден — `error`; проба не удалась (сеть, нет менеджера) — `warn`; менеджер недоступен на этой ОС — `info` |
| **compose** | Если в модуле есть compose-файлы и найден `docker`/`podman`: `compose config -q` | `error`; рантайма нет — `info` |

**Наборы scopes для L5.** ОС-scopes (`linux`, `windows`, `unix`, `cachyos`, …) активируются автоматически по ОС плана. Из остальных scopes модуля строятся наборы: «без scopes» и «каждый scope по отдельности». Модуль переопределяет наборы фикстурами (§5.5).

**Цели L5 по ОС.** Поле `os` модуля плюс дистрибутивы, для которых в модуле есть секции `[scope.<дистрибутив>]` (`arch`, `cachyos`, `debian`, `fedora`, … — значения, которые `detect-host-os` выдаёт как auto-scopes). Иначе модуль с `os = ["linux"]` и `[scope.cachyos]` никогда не получит план с активным `cachyos`: override `linux` включает только `linux` и `unix` ([src/state.nu:110](../../src/state.nu#L110)).

**ОС для L5 (решение пользователя: приблизительно, без изменений ядра).** Нативная ОС планируется без override; остальные ОС модуля — через `YGG_HOST_OS_OVERRIDE`. Это позволяет с одной машины до push поймать логические конфликты плана для всех ОС модуля: одна цель из двух секций, вложенность, затенение, scope-зависимые коллизии.

Override переключает scopes и менеджеры, но не всю файловую логику: сравнение путей без учёта регистра (`normalize-case`, [src/link.nu:79](../../src/link.nu#L79)) и разделитель в `resolve-link-targets` следуют реальной ОС, а `fs-windows` на реальном Windows всегда истинна ([src/state.nu:86-88](../../src/state.nu#L86-L88)). Поэтому:
* `link.nu` и `state.nu` ради `lint` не меняются;
* находки L5 для чужой ОС выводятся с пометкой «план для <os> построен на <host>; окончательная проверка — нативный прогон в CI» и полем `cross_os: true` в `--json`; severity при этом не понижается — логические конфликты от ОС не зависят;
* источником истины для каждой ОС остаётся нативный прогон в CI (§5.6), в том числе для коллизий, отличающихся только регистром.

**Зависимости.** План строится и без зависимостей (`sort-modules-dag` пропускает отсутствующие), а `preflight-check` выдаёт для них `missing_dependency` ([src/link.nu:1039-1054](../../src/link.nu#L1039-L1054)). Без фикстуры `lint` выполняет L5 полностью и понижает только `missing_dependency` до `warn` «зависимость не проверена»: где лежат репозитории зависимостей, знает только хост. Коллизии между модулем и его зависимостями проверяются только с фикстурой.

### 5.4. Пробы пакетов

Таблица `PROBE_ARGVS` в `src/pkg.nu`, по образцу `LISTING_ARGVS`: для каждого менеджера — способ проверить существование пакета без установки и правило, какой код выхода или ответ означает «не найден».

| Менеджер | Проба | Где доступна |
|---|---|---|
| winget | `winget show --exact --id <id>` | Windows |
| scoop | `scoop info <bucket/app>` (после добавления нужных бакетов) | Windows |
| pacman | `pacman -Si <pkg>` (после `pacman -Sy` во временную БД или в контейнере) | Arch-семейство |
| paru | AUR RPC `info` по HTTP | везде |
| apt / dnf / zypper | `apt-cache show` / `dnf info` / `zypper info` | соответствующий дистрибутив |
| brew | `brew info <formula>` | macOS (и Linux с brew) |
| mise | `mise ls-remote <tool>` (имя до `@`) | где установлен mise |
| cargo / pnpm / uv | реестры crates.io / npm / PyPI по HTTP | везде |

Менеджеры, недоступные на текущем хосте, дают `info` «проверено не здесь»: полное покрытие достигается матрицей CI. Для тестов — мок `YGG_MOCK_PKG_UNKNOWN` (список пакетов, которые проба считает несуществующими), действует только вместе с `YGG_MOCK_PKG_LOG`.

### 5.5. Фикстуры `ci/hosts/*.toml`

Необязательные виртуальные `host.toml` в репозитории модуля. Если каталог есть, L5 строится только по ним, вместо наборов по умолчанию.

```toml
# ci/hosts/work-laptop.toml
os = ["windows"]                  # необязательно: на каких ОС применять фикстуру

[[modules]]
name = "<этот модуль>"            # проверяемый модуль; сопоставляется по name из ygg.toml
scopes = ["work"]
config = { projects_dir = "~/projects" }

[[modules]]
name = "<зависимость>"
source = "https://github.com/<owner>/<repo>"   # git URL или путь относительно корня модуля
ref = "v1.2.0"                    # необязательно
```

Зависимости из фикстуры клонируются во временный каталог `lint` (это единственный сетевой доступ вне `--packages`).

### 5.6. Reusable workflow `module-check.yml`

Файл `.github/workflows/module-check.yml` в репозитории движка, `on: workflow_call`.

**Входы:**
* `ygg-version` — любой git ref движка (тег, ветка или SHA), по умолчанию версия, с которой выпущен сам файл. `scripts/release.nu prepare` обновляет это значение вместе с `YGG_VERSION` (у reusable workflow нет надёжного способа узнать собственный ref);
* `module-path` — путь к модулю внутри вызывающего репозитория, по умолчанию `.`;
* `packages` (bool, по умолчанию `true`);
* `os` — переопределение матрицы ОС (по умолчанию — из `ygg.toml` модуля).

**Jobs:**
1. `matrix` (ubuntu): читает `os` из `ygg.toml` и строит матрицу.
2. `lint` по матрице: checkout модуля, checkout `gidragir/ygg@<ygg-version>`, установка Nushell `0.116.1`, установка mise при mise-пакетах в модуле, затем `nu <engine>/bin/ygg.nu lint <module> --packages --os <os>`.

**Соответствие ОС раннерам:**

| `os` модуля | Раннер |
|---|---|
| `windows` | `windows-latest` |
| `macos` | `macos-latest` |
| `linux`, `ubuntu`, `debian` | `ubuntu-latest` |
| `arch`, `cachyos` | `ubuntu-latest` + контейнер `archlinux:latest` |
| `fedora` | `ubuntu-latest` + контейнер `fedora:latest` |
| прочее | `ubuntu-latest` с предупреждением в логе |

**Вызов из модуля** (`.github/workflows/ygg.yml`):

```yaml
name: ygg
on: [push, pull_request]
jobs:
  check:
    uses: gidragir/ygg/.github/workflows/module-check.yml@v0.4.0
```

## 6. Тесты и приёмка

Новый `tests/test_lint.nu`, все модули-фикстуры создаются внутри `with-temp-ygg`:

1. Отсутствующий источник в неактивном `[scope.work.links]` → `error` с путём относительно модуля и секцией объявления (#23).
2. Битый TOML в `links.toml`; `[scopes.x]` в `ygg.toml` → `warn`; неизвестный менеджер → `error`; отсутствующий источник `[save]` → `error`.
3. Синтаксическая ошибка в `setup.nu` → `error`.
4. Некорректное выражение scope → `error`.
5. Конфликт целей (одна цель из базовой секции и из `[scope.work]`, пути совпадают побайтно), проявляющийся только при `os = windows` и scope `work` → `error` при запуске на любой ОС; на не-Windows хосте у находки `cross_os: true`. Коллизии, отличающиеся только регистром, в этот тест не входят (их ловит только нативный прогон).
6. Модуль с `depends_on` без фикстуры → L5 выполняется, `missing_dependency` понижен до `warn`, код выхода 0; с фикстурой и локальной зависимостью (`source` — относительный путь) → `missing_dependency` нет, коллизия целей между модулем и зависимостью → `error`.
7. `--packages` с `YGG_MOCK_PKG_UNKNOWN` → `error` по неизвестному пакету; менеджер другой ОС → `info`.
8. Read-only: после `lint` в `YGG_HOME` из `with-temp-ygg` нет новых файлов, `HOME` песочницы не изменён, временные каталоги `lint` удалены (проверка в дочернем `^nu` с собственным `TMPDIR`/`TEMP`/`TMP`, AGENTS.md §2.1).
9. `--json` даёт список записей `{check, severity, target, detail, fix}`; код выхода 1 только при `error`.
10. Completions: `lint` присутствует во всех генераторах (тест RFC-052 на совпадение флагов покрывает это автоматически).

**CI движка:** в `ci.yml` добавляется job, который вызывает `module-check.yml` с `ygg-version: ${{ github.sha }}` и `module-path: tests/fixtures/module-sample` (Linux + Windows). Так reusable workflow проверяется на коде самого PR.

**Приёмка #38:** вызов из пяти строк в модуле-фикстуре проходит на всех ОС из его `os`; намеренно сломанная копия (отсутствующий источник в scope, несуществующий ID пакета) роняет соответствующий job с понятной находкой.

## 7. Риски и что проверить до реализации

* **winget на `windows-latest`.** Если не предустановлен — шаг установки в workflow; без него L6 для winget даёт только `warn`.
* **scoop под администратором.** Установщик scoop отказывается работать от администратора без явного флага; бакеты из имён пакетов (`extras/foo`) нужно добавлять до пробы.
* **`YGG_HOST_OS_OVERRIDE` в продуктовом пути.** До сих пор это был тестовый механизм. Решение §5.3 принимает его неполноту; нужно убедиться, что override, выставленный внутри `lint` через `with-env`, не протекает в дочерние процессы проб L6 и compose.
* **Лимиты API.** `mise ls-remote` ходит в GitHub API — в CI передаётся `GITHUB_TOKEN`; AUR RPC и реестры — пакетными запросами, а не по одному пакету.
* **Nushell в контейнерах.** `hustcer/setup-nu` в `archlinux`/`fedora` нужно проверить; запасной путь — пакет `nushell` из репозиториев дистрибутива.

## 8. Решения, принятые по ходу (на проверку)

* Находки `lint` в формате `doctor` (`{check, severity, target, detail, fix}`), чтобы `--json` и вывод были единообразными; поля `doctor` не переименовываются.
* Наборы scopes по умолчанию — «без scopes» и «каждый по отдельности», а не все сочетания: сочетания растут экспоненциально; нужные сочетания модуль задаёт фикстурой.
* Без фикстуры модуль с `depends_on` получает L5, а `missing_dependency` понижается до предупреждения.
* Файл и секция объявления есть в находках L1–L4 (собственный обход файлов); L5 сообщает `<модуль>: <ключ>`, отслеживание источника записи в объединённом манифесте не добавляется.
* L5 планирует и дистрибутивы, для которых в модуле есть `[scope.<дистрибутив>]`.
* У workflow есть входы `ygg-version` (любой ref) и `module-path`, чтобы CI движка проверял workflow на коде PR.
* Пометка чужой ОС — поле `cross_os` и текст в выводе, без понижения severity.
* `ygg-version` по умолчанию обновляется `scripts/release.nu`.
* `tests/test_phase2_modules.nu` удаляется в рамках этой работы (#35).
