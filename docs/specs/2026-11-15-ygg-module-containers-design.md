# RFC-059: Контейнеры модулей (compose) в ядре `ygg`

* **Дата:** 2026-11-15
* **Статус:** черновик, на утверждении
* **Затрагивает:** `bin/ygg.nu` (`add`, `apply`, `diff`, `remove`, `status`, `doctor`, новая `upgrade`), новый `src/container.nu`, `src/manifest.nu`, `src/link.nu` (preflight), `src/state.nu`, `tests/`

---

## 1. Зачем

Сейчас контейнеры живут только в модуле `ai-dotfiles` (`infra/stacks/hindsight`, `infra/stacks/khoj`), и управляются вручную: задачи `mise` (`docker compose up -d` / `down`) и bash-скрипт `scripts/ai-stack.sh`. `ygg` о них ничего не знает.

Когда контейнеры появятся в других модулях (пример: модуль `data-science` ставит `uv`, `python` и поднимает `postgres` для локальных проектов), каждый модуль будет заново кодить «поднять / обновить образы / пересоздать / выключить». Цель — чтобы модуль только **описывал** контейнеры обычным `compose.yml`, а жизненным циклом управлял `ygg` единообразно для всех модулей.

## 2. Цели, не-цели, анти-цели

**Цели**
1. Модуль объявляет контейнеры стандартным compose-файлом. Никакого собственного DSL поверх compose.
2. UX короткий и нативный:
   * `ygg add <module>` спрашивает, поднимать ли контейнеры модуля;
   * `ygg apply --containers [module...]` — включить и поднять;
   * `ygg apply --no-containers [module...]` — выключить (`down`);
   * `ygg upgrade --containers [module...]` — обновить образы и пересоздать контейнеры.
3. Без указания модуля команда действует на все подходящие модули.
4. Работает с `docker compose` и `podman compose` на Linux, macOS и Windows (Non-Admin), в рамках инварианта №4 `AGENTS.md`.

**Не-цели**
* Установка Docker/Podman и запуск их демонов. Это делают пакеты модуля (`packages.toml`) и `[services]` (например, `enable = ["docker.service"]` в `[scope.linux.services.systemd-system]`).
* Порядок запуска между контейнерами и systemd-службами (ollama → hindsight в `ai-stack.sh`). Остаётся в модуле. Порядок внутри одного стека задаёт `depends_on` самого compose.
* Интеграция `secrets.toml` / `config` из `host.toml` в переменные окружения compose. Compose читает свой `.env` рядом с файлом и окружение процесса, как обычно. Возможное расширение — отдельный RFC.
* Автообновление по расписанию.
* Миграция `ai-dotfiles` на новый механизм — отдельная задача в том репозитории (см. §9).
* Защита данных в bind-mount внутри каталога модуля (`./data:/var/lib/...`) при `ygg remove`: `remove-module` и сегодня удаляет каталог модуля целиком, включая файлы из `.gitignore`. Это общее поведение `remove`, не специфичное для контейнеров. Рекомендация для модулей: хранить данные в именованных томах (`volumes:`), а не в каталоге модуля. Ядро не разбирает `volumes:` compose-файла. *(решение автора дока)*
* Отслеживание изменений в `env_file:`, `include:`, Dockerfile и контексте сборки обычным `apply`. Для применения таких изменений: `ygg apply --containers <module>` (безусловный `up -d`) или `ygg upgrade --containers <module>` (пересборка). *(решение автора дока)*

**Анти-цели (провал, даже если «работает»)**
* Потеря данных: `ygg` никогда не удаляет тома (`down -v`) и образы (`--rmi`).
* Неожиданная остановка контейнеров обычным `ygg apply` без изменений в compose-файлах.
* Заметное замедление обычного `ygg apply` у модулей без контейнеров или без изменений.
* Захардкоженные имена модулей или стеков в ядре (инвариант №2).

## 3. Ограничения проекта

* **Инвариант №2 (чистота ядра):** `docker` и `podman` вводятся как белый список рантаймов `CONTAINER_RUNTIMES = ["docker", "podman"]`, по прецеденту менеджеров пакетов в `src/pkg.nu` и `SERVICE_MANAGERS` в `src/link.nu`. Ядро не интерпретирует содержимое compose-файла, кроме чтения необязательного верхнеуровневого `name:` (§5.2).
* **Инвариант №1 (ZERO HOST MUTATION):** тесты не вызывают реальный рантайм; мок через `YGG_MOCK_PKG_LOG` (§7).
* **Read-only команды:** `status`, `doctor` (без `--fix`), `diff` и `apply --dry-run` вызывают рантайм только на чтение (`compose version`, `compose ls`, `compose ps`).
* **Блокировка:** все мутирующие операции с контейнерами идут под `host.lock`.
* **Журнал v2:** новый шаг `containers` в `apply`.
* **Аргументы процессов:** команды собираются как argv-список, без интерполяции в строку шелла (как `build-service-cmd`).

## 4. Подходы

| Подход | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Отдельный слой контейнеров (выбран)** | Новый `src/container.nu`; секция `[containers]` в `ygg.toml`; флаг `containers` у модуля в `host.toml`; флаги в `add`/`apply`, команда `upgrade` | UX ровно как описан; логика в одном месте; не ломает существующие RFC | Новая подсистема и тесты |
| B. Менеджер `compose` в `[services]` (RFC-037) | Переиспользовать `enable`/`restart_on_change` | Готовый механизм триггеров | Семантика «перезапусти службу при смене ссылки» не покрывает `pull`/`down`, вопрос при установке и выбор модулей; пришлось бы ломать RFC-037 |
| C. Хелпер в SDK для `setup.nu` | Модуль сам вызывает `ygg container up` | Минимум изменений ядра | Код снова в каждом модуле — ровно то, от чего уходим |

Пользователь выбрал **A**.

## 5. Дизайн

### 5.1. Контракт модуля (`ygg.toml`)

Минимальный случай: в корне модуля лежит `compose.yml` — больше ничего не нужно.

Автообнаружение, если секции `[containers]` нет: первый существующий из `compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml` в корне модуля (порядок совпадает с порядком поиска самого `docker compose`).

Явное объявление (несколько стеков, нестандартные пути):

```toml
[containers]
files = ["infra/stacks/hindsight/docker-compose.yml", "infra/stacks/khoj/docker-compose.yml"]
```

* Если `[containers].files` задан, автообнаружение отключается.
* `[scope.<name>.containers].files` **добавляется** к базовому списку для активных скоупов (как пакеты в скоупах). Пример: стек только на `[scope.pc]`.
* Пути относительные к корню модуля; абсолютные пути и выход за пределы модуля (`..`) — ошибка preflight.
* `[containers] files = []` явно отключает автообнаружение (модуль без контейнеров при наличии файла в корне).

Каждый файл — один **стек**.

**Override-файл.** Поскольку `ygg` всегда передаёт `-f`, compose сам не подхватит соседний override. Чтобы поведение совпадало с ручным запуском, `ygg` проверяет рядом с файлом `<stem>.override.<ext>` (например, `compose.override.yml` для `compose.yml`, `docker-compose.override.yml` для `docker-compose.yml`) и, если он есть, передаёт его вторым `-f`. *(решение автора дока)*

**Входы стека для хэша:** основной compose-файл, override-файл (если есть) и `.env` в каталоге основного файла (если есть). *(решение автора дока)*

### 5.2. Имя проекта compose

Для изоляции стеков разных модулей `ygg` всегда передаёт `-p <project>`:

1. Если в compose-файле есть верхнеуровневый `name:` — используется он (нативное поведение compose, модуль сам управляет именем).
2. Иначе: `<module>`, если файл в корне модуля; `<module>-<имя родительского каталога файла>` в остальных случаях.

Имя нормализуется под требования compose (нижний регистр, `[a-z0-9_-]`, начинается с буквы/цифры). Два стека с одинаковым итоговым именем на хосте (в одном или разных модулях) — ошибка preflight.

### 5.3. Выбор пользователя (`host.toml`)

Решение «ставить ли контейнеры» — это пользовательская настройка, поэтому хранится в записи модуля в `host.toml`, рядом с `scopes` и `exclude`:

```toml
[[modules]]
name = "data-science"
repo = "gidragir/data-science"
containers = true
```

* `true` — контейнеры включены; `false` или отсутствие ключа — выключены.
* Ручная правка `containers = true` и последующий `ygg apply` поднимают стеки (декларативно).

Выбор рантайма и таймаут — в общем разделе `ygg` (по образцу `ygg.backups`):

```toml
[ygg.containers]
runtime = "podman"   # необязательно: "docker" | "podman"; по умолчанию автоопределение
timeout = 900        # секунды на одну команду compose; по умолчанию 600
```

Автоопределение: `docker compose version` → `docker`; иначе `podman compose version` → `podman`; иначе рантайма нет. Значение вне белого списка — ошибка preflight.

**Поддерживается только провайдер Compose v2** (решение пользователя). `podman compose` передаёт команды внешнему провайдеру; поддерживается только плагин `docker-compose` v2+. Провайдер `podman-compose` не поддерживается: у него нет `compose ls`, и `down -p <project>` без файла не работает. Проверка: вывод `<rt> compose version` должен указывать на Docker Compose версии 2 или выше. Иначе рантайм считается отсутствующим (`skipped_no_runtime`), а в предупреждении есть подсказка установить плагин `docker-compose` v2. То же самое при явном `runtime = "podman"`. Благодаря этому все команды из §5.5 (`compose ls`, `down` по имени проекта) одинаковы для `docker` и `podman`.

### 5.4. Состояние (`state.json`)

* `state.hashes."containers:<module>:<project>"` — хэш входов стека (§5.1) на момент последнего успешного `up -d`.
* `state.containers` — список активных стеков `[{ module, project, file, runtime }]`, поднятых `ygg`. Нужен, чтобы опускать стеки, исчезнувшие из манифеста, и стеки удалённых модулей, даже если файла уже нет (`compose -p <project> down` работает без `-f`).
* GC хэшей (`gc-state-hashes`) учитывает ключи `containers:*` активных стеков.

### 5.5. Команды

Команды compose (все argv, `cwd` не меняется, project directory по умолчанию — каталог файла, поэтому относительные пути томов в compose работают как при ручном запуске):

* поднять: `<rt> compose -f <file> [-f <override>] -p <project> up -d --remove-orphans` (сервисы с `build:` собираются compose только если образа ещё нет — нативное поведение)
* выключить: `<rt> compose -p <project> down` (без `-v`, без `--rmi`)
* обновить: `pull --ignore-buildable` → `build --pull` (только если в стеке есть сервисы с `build:`; ядро определяет это чтением YAML, как и `name:`) → `down` → `up -d --remove-orphans`. `--ignore-buildable` нужен, чтобы сервис с одновременно заданными `image:` и `build:` не ронял `pull`. *(решение автора дока)*

#### `ygg add <src> [--containers | --no-containers]`

Вопрос задаётся **после стейджинга и до preflight**: ответ влияет на preflight контейнеров (коллизии имён проектов, пути), а контракт RFC-012/020 требует регистрировать модуль в `host.toml` только после успешного preflight. Ответ передаётся в виртуальную запись модуля (`extra_modules`) и пишется в `host.toml` вместе с регистрацией. *(решение автора дока)*
* В модуле нет стеков → ничего не спрашивается, ключ `containers` не пишется.
* Есть стеки и задан флаг → `containers = true/false` по флагу.
* Есть стеки, флага нет, терминал интерактивный → вопрос
  `Module 'data-science' declares containers (compose.yml). Start them now? [y/N]: `
  Ответ пишется в `host.toml`.
* Неинтерактивно (`not (is-terminal --stdin)` или `YGG_NONINTERACTIVE=1`) → `containers = false`, печатается подсказка `ygg apply --containers data-science`.
* `add --dry-run` ничего не спрашивает и не пишет.

Далее обычный `apply-plan`; при `containers = true` шаг контейнеров (§5.6) поднимает стеки.

#### `ygg apply [...modules] [--containers | --no-containers]`

* Позиционные `...modules` допустимы **только** вместе с `--containers` или `--no-containers`; иначе ошибка. Одновременно оба флага — ошибка. Неизвестный модуль или модуль без стеков — ошибка до любых мутаций.
* `--containers [mods]`: целевые модули (указанные, либо все модули со стеками) получают `containers = true` в `host.toml`, затем выполняется полный `apply-plan`, а шаг контейнеров для целевых модулей делает `up -d` безусловно (без проверки хэша).
* `--no-containers [mods]`: целевые модули (указанные, либо все с `containers = true`) получают `containers = false`, затем полный `apply-plan`; шаг контейнеров делает для них `down`.
* Запись в `host.toml` выполняется под host lock до `apply-plan`. При `--dry-run` `host.toml` не меняется, а план печатается так, как если бы флаг применился.
* Без флагов — обычный `apply`, шаг контейнеров работает по §5.6.

#### `ygg upgrade --containers [...modules]`

* Новая команда верхнего уровня. Без `--containers` — ошибка с подсказкой (задел под будущие цели обновления, но сейчас поддерживается только эта).
* Цели: указанные модули (каждый обязан иметь `containers = true`, иначе ошибка с подсказкой `ygg apply --containers <module>`), либо все модули с `containers = true`.
* Для каждого стека: `pull` → при успехе `down` → `up -d --remove-orphans`. Если `pull` упал, стек не трогается (контейнеры продолжают работать), стек помечается как неуспешный.
* Не выполняет `git`-обновление модулей и не запускает `apply-plan`. Берёт host lock. Поддерживает `--dry-run` (печатает команды) и `--no-lock`.
* После успешного `up -d` обновляет хэш в `state.hashes`.
* Код выхода 1, если хотя бы один стек не обновился; остальные стеки всё равно обрабатываются.

#### `ygg remove <module>`

Перед `unlink-module`: `down` для всех стеков модуля из `state.containers` (тома остаются). Нет рантайма или `down` упал — предупреждение, удаление модуля продолжается; запись в `state.containers` при этом снимается, а в сообщении указывается команда для ручного `down`.

#### `ygg status` / `ygg doctor`

* `status`: колонка `containers` — `-` (стеков нет), `off`, `on N/M running` (по одному вызову `compose ls --format json`). Если рантайма нет — `on (no runtime)`. Строго read-only.
* `doctor`: находки уровня warn — включённые стеки, которые не запущены; включённые модули при отсутствующем рантайме; записи `state.containers` для стеков, которых больше нет в манифестах. `doctor --fix` для этих находок ничего не делает (подсказывает `ygg apply`), чтобы не поднимать контейнеры неявно.

### 5.6. Шаг `containers` в `apply-plan`

Новый шаг журнала `containers` — после `services` и до `finalize`. Важно: `[services]` делает `systemctl enable` без `--now`, поэтому на свежей машине демон в том же `apply` может быть не запущен; Docker Desktop на macOS/Windows тоже часто не запущен.

**Доступность рантайма.** Перед первой мутирующей командой шаг один раз проверяет, что демон отвечает (`<rt> compose ls`; провайдер проверен по §5.3). Три исхода:
* клиента нет → `skipped_no_runtime`;
* клиент есть, демон не отвечает → `skipped_daemon_down`;
* доступен → выполнение.

Оба `skipped_*` при обычном `apply` — предупреждение с подсказкой (запустить демон / Docker Desktop и повторить `ygg apply`), шаг журнала — `COMMITTED`, код выхода 0, хэши не записываются (следующий `apply` повторит попытку). При явном `--containers`/`--no-containers` и в `upgrade` — ошибка. `status` показывает `on (daemon down)`, `doctor` — warn. *(решение автора дока)*

Для каждого стека:
1. Стек в `state.containers`, но модуль удалён из плана, стек исчез из манифеста или модуль выключен → `down`, снять из `state.containers`.
2. Модуль включён и (стек — цель `--containers`, или стека нет в `state.containers`, или хэш изменился) → `up -d --remove-orphans`; при успехе записать хэш и стек в состояние.
3. Иначе — ничего (рантайм не вызывается).

Если включённых стеков нет и в `state.containers` пусто — рантайм не определяется и не вызывается вообще.

Ошибки: неуспешная команда при доступном рантайме не прерывает остальные стеки; шаг помечается `FAILED`, ошибка добавляется в итоговый список ошибок `apply` (как у `services`), код выхода 1.

`--dry-run`: печатаются строки
`  CONTAINER       up data-science  (data-science: compose.yml)`
`  CONTAINER       down ai-dotfiles-khoj  (ai-dotfiles: removed from manifest)`
и учитываются в счётчике изменений.

### 5.7. Preflight

В `preflight-check` (до любых мутаций), только для стеков, которые шаг собирается поднимать:
* compose-файл существует и является файлом;
* путь внутри модуля;
* имена проектов уникальны на хосте;
* `ygg.containers.runtime` из белого списка.

Наличие рантайма в preflight не проверяется (см. §5.6).

### 5.8. Кроссплатформенность

* Ядро только вызывает CLI `docker`/`podman`; установка рантайма — ответственность модуля и пользователя. На Windows без прав администратора Docker Desktop не ставится, поэтому отсутствие рантайма — штатная ситуация с понятным предупреждением.
* Пути к compose-файлам передаются через `path expand -n` (на Windows — `to-win32-path`).
* Никаких Unix-only механизмов (`systemd`-юниты для compose, сокет как единственный транспорт).
* Таймаут — общий `run-with-timeout` с `kill-job-tree`; по умолчанию 600 с, т.к. `pull` больших образов долгий.

## 6. Пример: модуль `data-science`

```text
data-science/
├── ygg.toml          # name, os, description
├── packages.toml     # uv, python
└── compose.yml       # services.postgres: image postgres:17, volume pgdata
```

```console
$ ygg add gidragir/data-science
Module 'data-science' declares containers (compose.yml). Start them now? [y/N]: n
Added module data-science
...
$ ygg apply --containers data-science      # позже: поднять postgres
$ ygg upgrade --containers                 # вышел новый postgres: pull → down → up -d
$ ygg apply --no-containers data-science   # выключить
```

## 7. Тестирование

* Мок: при непустом `YGG_MOCK_PKG_LOG` каждая команда пишется строкой `container: <argv через пробел>`, рантайм не определяется (берётся `ygg.containers.runtime` или `docker`). `YGG_MOCK_CONTAINER_FAIL` — список подстрок argv, команды с которыми «падают». В песочнице без мок-лога — статус `skipped_sandbox`, ничего не выполняется.
* `tests/run.nu` уже скрывает все `YGG_*`; новые переменные под это попадают автоматически.
* Новый файл `tests/test_container.nu`, сценарии минимум:
  * автообнаружение файла, `files`, `files = []`, скоупы;
  * имя проекта: по умолчанию, из `name:`, коллизия → preflight;
  * `add`: флаги, неинтерактивный режим, вопрос не задаётся без стеков, `--dry-run` не пишет `host.toml`;
  * `apply --containers` / `--no-containers` с модулями и без; ошибки аргументов;
  * обычный `apply`: без изменений рантайм не вызывается; изменение файла → `up -d`; стек убран из манифеста → `down`;
  * `upgrade`: порядок `pull → down → up -d`; упавший `pull` не вызывает `down`; модуль выключен → ошибка;
  * `remove` вызывает `down` без `-v`;
  * ни одна команда в логе не содержит `-v`, `--volumes`, `--rmi`;
  * `status`/`doctor`/`diff` не пишут в состояние.

## 8. Решения, оставленные реализатору

* Внутреннее устройство `src/container.nu` и разбиение на функции.
* Точный формат строк `status` и сообщений.
* Чтение `name:` из compose — через `open` (YAML) Nushell; если файл не парсится, использовать имя по умолчанию и не падать.

## 9. Последствия для `ai-dotfiles` (отдельная задача)

* Объявить `[containers] files = [...]` для `hindsight` и `khoj`.
* В compose-файлах заданы `container_name: hindsight` / `khoj`: первый `up` под новым именем проекта столкнётся с контейнерами, поднятыми вручную. Варианты: добавить в compose-файлы `name: hindsight` / `name: khoj` (совпадёт с текущими проектами по имени каталога) либо один раз выполнить `docker compose down` в старых каталогах.
* Задачи `mise` `*-up`/`*-down` можно заменить на `ygg apply --containers ai-dotfiles` / `--no-containers`.
